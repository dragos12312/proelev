# ProElev — Database design

This document covers the persistence layer added in Assignment 3 (Bronze).

## Stack

- **Database:** SQLite (file `proelev.db` next to the backend, configurable via
  `DATABASE_URL`). Picked over Postgres/MySQL because the assignment forbids
  manual schema and SQLite needs zero install on the demo machine, while still
  being a real relational DB with ACID transactions, foreign keys, check
  constraints, and indexes.
- **ORM:** SQLAlchemy 2.0 — the most widely used Python ORM, mature, type-safe,
  works first-class with FastAPI through a `Depends(get_db)` session pattern.
- **Migrations:** Alembic — official migration tool for SQLAlchemy. The schema
  is **not** written by hand; it is autogenerated from the ORM model classes
  (`models.py`) with `alembic revision --autogenerate`, then applied with
  `alembic upgrade head`.

## 3NF proof, table by table

A relation is in **3NF** iff every non-key attribute is:
1. atomic (1NF), and
2. fully functionally dependent on the whole primary key (2NF), and
3. non-transitively dependent on the primary key (3NF — no `non-key → non-key`
   functional dependency).

All six tables use a single-column surrogate `id` primary key, so 2NF
(no partial dependency on a composite key) is trivially satisfied.

### subject `(id PK, name UNIQUE)`
1NF: scalar columns. 2NF: trivial. 3NF: `name` depends only on `id` — there is
no other non-key attribute, so no transitive dependency is possible. ✅

### school_class `(id PK, name UNIQUE)`
Same shape as `subject`. ✅

### homework `(id PK, title, subject_id FK, class_id FK, due_date, description, file_name)`
1NF: every column is scalar. There are no list-valued or nested fields.
2NF: trivial (single-column PK).
3NF: each non-key attribute depends only on `id`.
- `title`, `due_date`, `description`, `file_name` — properties of the homework
  itself, no functional dependency on each other.
- `subject_id` and `class_id` — FK columns; they reference the lookup tables.
  Crucially, the **subject name** and **class name** are *not* stored in this
  table — they live exactly once in `subject.name` and `school_class.name`.
  This is the change versus the in-memory model: previously the same string
  `"Matematică"` was repeated in every row, which was a transitive dependency
  (`subject_name` depended on `subject_id` if we had introduced one). After
  normalising into the lookup tables that transitive dependency is gone. ✅

### student `(id PK, homework_id FK, name, date_time, grade)`
1NF: scalar. 2NF: trivial. 3NF: each non-key attribute depends only on the
student's `id`. `name`, `date_time`, `grade` are independent of each other.
A `CHECK (grade IS NULL OR grade BETWEEN 1 AND 10)` constraint enforces the
domain at the DB level, not just in Pydantic. ✅

### comment `(id PK, homework_id FK, author, text, created_at)`
Identical analysis to `student`. ✅

### user `(id PK, email UNIQUE, password, name)`
Standalone table, no FKs. `email` is unique, all other attributes depend
only on `id`. ✅

### Why the current schema avoids the most common 3NF trap

Embedding subject/class as plain strings inside `homework` would technically
still be in 3NF if you treat the strings as atomic values with no other
attributes about them. The reason we extracted lookup tables is twofold:
(1) it eliminates string repetition (storage win on real datasets), and
(2) it makes adding attributes to subjects (like a colour or icon) trivial
without restructuring `homework` — i.e. it future-proofs the schema against
a 3NF violation that *would* appear the moment subjects acquire any second
attribute.

### Auth/role schema (relational, in the same SQLite DB)


`role` and `permission` are joined many-to-many through `role_permission`.
A user has exactly one `role`. Both tables are in 3NF — single-column PKs,
every non-key attribute (`role.name`, `permission.code`) depends only on `id`.
The seeder fills two roles (`admin`, `user`) and 15 permission codes; admin
gets all of them, normal users get a read-and-comment subset.

The migration that adds these tables (`alembic/versions/173a9d4e9ae9_*`) seeds
the role/permission rows **inside** the `upgrade()` function so a NOT NULL
`user.role_id` can be added safely (existing user rows get backfilled to admin
before the default is dropped).

### Chat — TinyDB (NoSQL) + WebSockets

The chat layer is the silver "real-time chat with NoSQL + WebSockets"
requirement. We deliberately use a **separate** datastore from the SQL one,
because chat messages are append-only document data and SQL is overkill for
them.

**Storage:** TinyDB, a single-file JSON document store. Path is
`./chat.json` by default, configurable via `CHAT_DB_PATH`.

**Two collections:**
- `rooms` — `{id, type, name, participants[]}` where type is `global`, `dm`,
  or `room`.
- `messages` — `{id, room_id, author_id, author_name, text, created_at}`.

**Room types:**
- `global` — auto-created, everyone joins it on connection. One per server.
- `dm` — created on demand when a user clicks another user's name. The
  `participants` array is sorted, so look-up is idempotent (`get_or_create_dm`).
- `room` — special topic rooms, **admin only** can create them. The chosen
  user IDs go into `participants`; non-participants get 403 on history reads
  and silent ignores on WebSocket subscribes.

**WebSocket protocol** at `/chat/ws`:
- `{type:"hello", user_id, user_name}` → server replies `{type:"ready"}` and
  auto-subscribes the client to the global room.
- `{type:"subscribe", room_id}` → server adds room to the client's set if the
  user is allowed to see it.
- `{type:"message", room_id, text}` → server persists via TinyDB and broadcasts
  `{type:"message", room_id, message:{...}}` to every client subscribed to
  that room.

**How to demo two-user chat:**
1. Start the server: `python -m uvicorn main:app --host 0.0.0.0 --port 8000`.
2. On the client machine, run the frontend with `VITE_API_URL` pointing at
   the server.
3. Open one browser window and log in as `admin@proelev.ro` / `Admin123`.
4. Open a second browser window (or a private/incognito tab so sessionStorage
   is independent) and log in as `user@proelev.ro` / `Parola123`.
5. Click the chat button (💬) in the top right of either window. Both windows
   are auto-subscribed to the **Global** room. Type a message in one — it
   appears in the other instantly.
6. To DM, click the other user's name in the **Persoane** list. The DM room
   is created on first message and reused after that.
7. To create a topic room, log in as admin, type a name in the
   "Camera nouă" input and click *Creează*. All other users get added
   automatically.

### Frontend role gating

After login, the user object (including `role` and the `permissions[]` array)
is saved to `sessionStorage`. `src/utils/auth.js` exposes `hasPerm(code)` and
`isAdmin()` so views can hide buttons:
- "ADAUGĂ TEMĂ" button on `/homeworks` is hidden unless `homework_create`.
- "Șterge" button on every homework row is hidden unless `homework_delete`.
- "MODIFICĂ" button on the homework detail page is hidden unless
  `homework_update`.
- "Camera nouă (admin)" panel inside the chat sidebar only renders when
  `isAdmin()` is true.

The backend also enforces the admin-only chat-room creation at the API
level (returns 403 to non-admin callers).

## Gold additions — audit logging + malicious-behaviour detection

### action_log + observation tables

```
 ┌──────────────────────────┐
 │ action_log               │
 │ id (PK)                  │
 │ user_id     FK→user      │   nullable, anonymous hits get null
 │ role_id     FK→role      │   captured at log time so role changes
 │ action       TEXT        │   short code, e.g. "homework.delete"
 │ target_type  TEXT        │   "homework" | "student" | "comment" | ...
 │ target_id    INT         │   id parsed out of the URL
 │ method       TEXT        │   GET / POST / PUT / DELETE
 │ path         TEXT        │   raw URL path
 │ status_code  INT         │   HTTP status returned
 │ ip_address   TEXT        │   request.client.host
 │ details      TEXT        │   JSON blob (e.g. query string)
 │ created_at   DATETIME    │   indexed
 └──────────────────────────┘
 indexes: (user_id, created_at) and (created_at) — drives detector queries

 ┌──────────────────────────┐
 │ observation              │
 │ id (PK)                  │
 │ user_id     FK→user UNIQ │   one row per flagged user
 │ reason      TEXT         │   semicolon-joined list of triggered rules
 │ score       INT          │   highest score seen so far
 │ first_flagged_at DATETIME│   never overwritten
 │ last_flagged_at  DATETIME│   updated on every fresh flag
 │ dismissed   INT (0|1)    │   admin can clear, fresh flag re-opens
 └──────────────────────────┘
```

Both tables are in 3NF — single-column PKs, every non-key attribute depends
only on the row id.

### Audit middleware (`audit_middleware.py`)

Registered globally on the FastAPI app. Runs after every HTTP request, in
this order:

1. Look at `path` — skip the OpenAPI/Swagger noise (`/docs`, `/openapi.json`,
   `/redoc`, `/favicon.ico`) and the health check (`/`).
2. Read `X-User-Id` header (sent automatically by `api.js` after login). If
   absent or unparseable, `user_id` is null — anonymous probes are still
   logged.
3. Classify the route through `_ROUTE_RULES` (a method+path regex table) into
   a short action code like `homework.delete` or `chat.dm.open`. Unknown
   routes get a generic `http.<method>` code so even unexpected traffic shows
   up in the log.
4. Insert the `ActionLog` row with method, path, status, IP, role, and the
   JSON-encoded query string in `details`.
5. If the request was authenticated, run `detector.update_observation(db,
   user_id)` synchronously — this is intentional, the lab teacher should see
   the observation list update on the very next admin-panel refresh, no
   background task to wait for.

Detector failures are caught and rolled back so they never break the user's
request.

### Detector rules (`detector.py`)

Tunable constants at the top of the file. Each rule scans a 60-second rolling
window of the user's `action_log` rows and contributes points to the user's
score. Score `>= 10` flags the user into `observation`.

| Rule                  | Trigger                                       | Points |
| --------------------- | --------------------------------------------- | ------ |
| Request flood         | `> 60` requests in the window                 | 5      |
| Mass delete           | `> 5` successful DELETEs in the window        | 7      |
| Forbidden spam        | `> 3` HTTP 403s in the window                 | 6      |
| Validation spam       | `> 10` HTTP 422s in the window (fuzzing)      | 4      |
| Privilege escalation  | non-admin attempting an admin-only action     | 10     |

Privilege escalation is the loudest rule on purpose — even a single attempt by
a normal user to hit `homework.delete`, `chat.room.create`,
`admin.observation.read`, etc. immediately puts them on the observation list.

When a user is re-flagged, `first_flagged_at` is preserved (audit trail) and
`last_flagged_at` is bumped to now. A previously dismissed observation is
automatically un-dismissed if the user gets flagged again.

### Admin endpoints (`routers/admin.py`)

All three endpoints take `user_id` as a query param and `_require_admin`
returns 403 if the caller is not an admin.

- `GET /admin/logs?user_id=…&page=1&pageSize=50&only_user_id=…` — paginated,
  newest first, optionally filtered to a single user. Each row includes the
  user name and role at log time.
- `GET /admin/observations?user_id=…&include_dismissed=false` — flagged users
  with name, email, role, score, reason, first/last seen, dismissed flag.
- `POST /admin/observations/{flagged_user_id}/dismiss?user_id=…` — clears the
  flag (sets `dismissed=1`).

### Admin Panel UI (`/admin`)

Vue view that auto-refreshes every 5 seconds, visible only to users with the
admin role (route guard plus the `ADMIN` sidebar item is conditional on
`isAdmin()`). Two cards stacked vertically:

1. **Lista de observație** — table of currently-flagged users with a
   `Dismiss` button per row. Toggle to include previously-dismissed entries.
2. **Activitate recentă** — color-coded action log table (HTTP method pills,
   status code badges). Filter by user id.

2. Log in as `admin@proelev.ro` in one browser, navigate to **ADMIN** in the

## Assignment 4 — Authentication, authorization, HTTPS

### Password storage

User passwords are stored as **bcrypt** hashes in the `user.password_hash`
column. Migration `19b052b1c739` replaces the old plain-text `user.password`
column, re-hashing any existing rows inline so no data is lost.

Hashing/verifying lives in `src/backend/auth.py` (`hash_password`,
`verify_password`), both implemented on top of `passlib.CryptContext`. Two
hashes of the same password produce different output (per-row salt), and the
verify call is constant-time.

### Tokens, sessions, and sliding refresh

Sessions are stateless JWTs signed with HS256 using `SECRET_KEY` from env
(with a 48-char dev default). The payload is `{sub, role, iat, exp}`. Every
token expires `ACCESS_TOKEN_MINUTES` after issue, default 30 minutes.

Inactivity timeout is implemented as a **sliding window**:
- `RefreshTokenMiddleware` runs after each request.
- If the request carried a valid bearer token, the middleware mints a fresh
  token with the timer reset and ships it back in the `X-Refresh-Token`
  response header (and exposes it via `Access-Control-Expose-Headers`).
- The frontend's `_handleSessionHeaders` swaps the fresh token into
  sessionStorage on every response.
- If a request arrives with an expired/invalid token, the middleware does
  not refresh — the route returns 401, the frontend logs out and bounces
  to `/login`.

Net effect: the user stays logged in as long as they touch the app within
any 30-minute window; ~30 minutes of inactivity logs them out.

### Auth endpoints

- `POST /auth/login` — body `{email, password}`, returns
  `{access_token, token_type, user:{id, email, name, role, permissions}}`.
- `POST /auth/register` — body `{name, email, password}`, creates a new row
  with the `user` role. Password rules: min 6 chars, at least one letter
  and one digit. Duplicate email → 409.
- `GET  /auth/me` — protected, returns the caller. The frontend hits this
  on startup to validate the cached token before showing the home page.

### Protected routes

`get_current_user` and `get_current_admin` (in `auth.py`) are FastAPI
dependencies that pull the bearer token from `Authorization`, decode it,
and look the user up. Without a valid token, every protected route returns
401 with `WWW-Authenticate: Bearer`. Non-admins hitting an admin-only
route get 403.

Routers using these dependencies:
- `/admin/*` — `Depends(get_current_admin)` on every endpoint.
- `/chat/*` — `Depends(get_current_user)` on every REST endpoint. The
  WebSocket cannot carry headers on the handshake, so the client sends the
  token inside the first `hello` message instead.
- `/auth/me` — `Depends(get_current_user)`.

### HTTPS

Self-signed cert generated by `src/backend/make_cert.py`:
```
python make_cert.py 192.168.x.y      # add the host's LAN IP as a SAN
```
The script writes `certs/key.pem` and `certs/cert.pem` and prints the
matching uvicorn command:
```
python -m uvicorn main:app --host 0.0.0.0 --port 8000 \
    --ssl-keyfile certs/key.pem --ssl-certfile certs/cert.pem
```
The certs folder is git-ignored. On the client machine, the browser will
show a security warning the first time — click *Advanced → Proceed* once
per browser session and the demo continues.

The frontend reaches HTTPS by setting `VITE_API_URL=https://192.168.x.y:8000`
in the client's `.env.local`. WebSocket connections automatically switch
to `wss://` because `api.js` derives the WS scheme from the HTTP base URL.

### Frontend session handling

- `src/utils/auth.js` keeps `currentUser` and `authToken` as reactive refs
  pulled from `sessionStorage` (`currentUser` + `authToken` keys).
- `setSession(user, token)` is called by both Login and Register on success.
- Every `fetch` in `src/api.js` attaches `Authorization: Bearer …` and runs
  `_handleSessionHeaders` to swap in the refresh token or trigger a
  bounce-to-login on 401.
- `RegisterView.vue` mirrors `LoginView.vue` styling, calls `/auth/register`
  and auto-logs-in on success.

### Tests

- `test_auth.py` — 23 tests: bcrypt round-trip + collision-resistance,
  login success/wrong password/unknown user/case-insensitive email,
  protected route auth (missing/bogus/wrong-signature/expired tokens),
  register validation (password rules, email format, duplicate, hash
  stored), sliding refresh header present/usable/absent.
- `test_silver.py` and `test_gold.py` were updated to use real tokens
  instead of the temporary `?user_id=` query parameter and `X-User-Id`
  header that earlier assignments used.

Final test count: **180 tests passing, 96% line coverage**.

## Assignment 4 Silver — 3-factor auth, sessions, password recovery

### Schema additions (migration `527d1b8966c2`)

```
 ┌──────────────────────────┐
 │ session                  │
 │ id (PK)                  │
 │ user_id      FK → user   │
 │ jti          UNIQUE      │   matches the JWT's jti claim
 │ created_at   DATETIME    │
 │ last_active_at DATETIME  │   bumped by get_current_user
 │ revoked      INT (0|1)   │   logout sets this to 1
 └──────────────────────────┘

 ┌──────────────────────────┐
 │ login_challenge          │   3-factor login state machine
 │ id (PK)                  │
 │ user_id      FK → user   │
 │ challenge_id UNIQUE      │   opaque id the client passes between steps
 │ email_code   STR(10)     │   6-digit code sent via the mock inbox
 │ email_verified INT       │   set to 1 after factor 2 passes
 │ completed    INT         │   set to 1 once a token has been issued
 │ created_at, expires_at   │   10-minute TTL
 └──────────────────────────┘

 ┌──────────────────────────┐
 │ password_reset           │
 │ id (PK), user_id, token  │   single-use, 30-minute TTL
 │ used INT, expires_at     │
 └──────────────────────────┘

 user.security_question      added to user, plus
 user.security_answer_hash   bcrypt-hashed answer used by factor 3
```

### 3-factor login flow

Factor 1 — `POST /auth/login` `{email, password}`
  - bcrypt-verify the password
  - create a `login_challenge` row with a fresh `email_code`
  - "send" an email via the mock inbox (TinyDB)
  - return `{challenge_id, next: "email_code"}`

Factor 2 — `POST /auth/login/verify-email` `{challenge_id, code}`
  - look up the challenge, reject if expired or completed
  - compare the code, set `email_verified=1`
  - return `{challenge_id, security_question, next: "security_question"}`

Factor 3 — `POST /auth/login/verify-question` `{challenge_id, answer}`
  - require `email_verified=1`
  - bcrypt-verify the lowercase-trimmed answer against
    `user.security_answer_hash`
  - mark the challenge `completed=1`
  - mint a fresh `Session` row + JWT and return the standard
    `LoginResponse {access_token, token_type, user}`

The seeded admin and user accounts have the security question
"Care este numele aplicației?" with answer "proelev" so the demo
runs out of the box.

### Token claims and `require_perm` dependency

Every token now carries `{sub, role, perms[], jti, iat, exp}`. The
permission codes are baked into the JWT so a dependency like
`Depends(require_perm("homework_delete"))` reads from the token instead
of hitting the DB. The bronze `get_current_user` still does one DB hit
to validate the `jti` and bump `last_active_at`.

### Session management

- Login mints a `Session` row keyed by a random 32-byte URL-safe `jti`.
- Every authenticated request looks up the row by `jti`; if `revoked=1`
  the request returns 401.
- `POST /auth/logout` sets `revoked=1` on the caller's session. The same
  JWT becomes unusable, even though it's still cryptographically valid.
- Password reset also revokes every active session for the user so an
  attacker who guessed the password is kicked out.
- `last_active_at` is bumped on every successful request, giving
  admins a recent-activity heartbeat (visible in `session.last_active_at`).

### Password recovery

`POST /auth/forgot` `{email}` — always returns 200 to avoid leaking
account existence. If the user exists, a 30-minute single-use reset
token is created and "emailed" via the mock inbox.

`POST /auth/reset` `{token, new_password}` — consumes the token, sets
the new bcrypt hash, marks the reset row `used=1`, and revokes every
session the user had.

### Mock email inbox

`src/backend/email_service.py` writes messages to a TinyDB file at
`EMAIL_DB_PATH` (default `./email.json`). Endpoints:
- `GET /auth/inbox` — protected; returns the caller's mail (admin sees all).
- `GET /auth/inbox/last?to=…` — public; the latest message for a given
  address. Lets unauthenticated flows (login factor 2, password reset)
  look up the code without first needing to be logged in. Real email
  would never expose this; the mock inbox is local-only.

`src/views/InboxView.vue` renders both flavours so the lab teacher can
watch codes arrive in real time during the demo.

### Frontend flow

- `LoginView.vue` is a three-step wizard with progress dots, switching
  between password → code → security-question without changing route.
- `RegisterView.vue` collects name, email, password, and a security
  question + answer (drop-down with four canned questions).
- `ResetPasswordView.vue` is a two-step recovery flow: enter email,
  then paste the code + new password.
- `AppProfile.vue` (avatar) gets a logout menu that calls
  `/auth/logout` and clears `sessionStorage`.
- `api.js` ships `Authorization: Bearer …` on every request and uses
  the `X-Refresh-Token` response header from the sliding-refresh
  middleware so the inactivity timer resets on every authenticated hit.

### Tests

- `test_auth_silver.py` adds **20 new tests**:
  3-factor happy path; each factor failing in isolation; expired
  challenge; logout revokes; revoked session blocks admin routes;
  forgot creates token + emails; unknown email still 200;
  reset is single-use; reset wipes existing sessions; admin JWT has
  every permission; user JWT is a strict subset; private inbox per
  user; admin inbox sees everything.
- All earlier bronze/silver/gold tests were updated to walk the
  3-factor flow via a shared `_test_login.py` helper, so the rest of
  the suite still passes.

Final count: **201 tests passing**, frontend builds and the 9 vitest
tests still green.

## Assignment 4 Gold — Hack the planet, the defense surface

The lab Gold challenge ships you to the room with two goals: attack
your peer's app, and protect your own. Attack tooling lives in
`attack/`; defenses live in the backend across one new module and a
handful of additions to existing files.

### Defense layers, in order

A request to the backend traverses this stack:

```
client ─→ CORS ─→ AUDIT ─→ DEFENSE ─→ REFRESH ─→ route handler
                       ↑          ↑
                       │          └ rate limit, body cap, sec headers
                       └ writes audit_log even for refused requests
```

So a 429 from defense still ends up in the `action_log` table, and the
admin panel renders it like any other event. Same for the 413 body
limit. That's the audit trail the lab teacher will look at.

### 1. `defense_middleware.py`

Three responsibilities in one ASGI middleware:

| Concern | How |
| --- | --- |
| Per-IP rate limit | Sliding-window counter keyed by (bucket, ip). `/auth/*` has its own tighter bucket (default 20 req / 60 s) versus the general bucket (120 req / 60 s). |
| Request size cap | Reads `Content-Length` before the body, returns 413 if the payload would exceed `MAX_BODY_BYTES` (default 1 MB). |
| Security headers | Stamps every response with HSTS, X-Frame-Options=DENY, X-Content-Type-Options=nosniff, Referrer-Policy, and a Content-Security-Policy. |

Limits are tunable via env vars: `RL_GENERAL_LIMIT`,
`RL_GENERAL_WINDOW_SEC`, `RL_AUTH_LIMIT`, `RL_AUTH_WINDOW_SEC`,
`MAX_BODY_BYTES`.

### 2. `login_throttle.py`

Brute-force defense for `/auth/login` factor 1. Tracks failed
attempts per (IP, email) pair. After `MAX_FAILURES` (default 5) bad
passwords inside `WINDOW_SEC` (default 120 s), the pair is locked
out for `LOCK_DURATION` (default 5 minutes), with a `Retry-After`
header on every rejected attempt. A successful login resets the
counter for that pair.

This is independent of the per-IP rate limit — even if the attacker
stays under the bucket cap, they'll trip the throttle once they
target the same email five times.

### 3. WebSocket flood guard (in `routers/chat.py`)

Each connected client keeps a deque of recent message timestamps.
More than `WS_FLOOD_LIMIT` (default 30) messages inside
`WS_FLOOD_WINDOW` (default 10 s) and the server sends an error
frame and closes the socket with code 1008. Stops chat spam dead.

### 4. Detector auto-revoke (in `detector.py`)

The Gold-3 detector already scores users on abnormal activity. New
in this assignment: once the score crosses `BLOCK_THRESHOLD`
(default 25 — higher than the 10 observation threshold), every
active session for that user gets `revoked=1`. The attacker's
in-flight bearer token stops working on the very next request. They
can log in again, but the burst is cut off.

### 5. HTTPS in transit

Still the bronze cert. The point in Gold is that Wireshark on a
peer's machine will show TLS handshake + opaque ciphertext, not the
plaintext password and token a non-HTTPS run would leak.

### Tests

`test_defense.py` adds **10 tests** spanning every layer:
- security headers stamped on every response, including 429s
- 413 on oversized requests
- general bucket rate limit
- auth bucket is strictly tighter than general
- brute-force throttle locks the (ip, email) pair
- successful login clears the throttle
- WebSocket flood disconnects the spammer
- detector auto-revokes sessions at `BLOCK_THRESHOLD`

The earlier 201 tests still pass; the conftest reset fixture clears
the in-memory rate-limit + throttle state between tests.

Final count: **211 tests passing, 95% line coverage** (was 96%; new
defense code is at 92–98% per module).

### How the lab demo works

You'll have two terminals open on the server box plus a browser on
the client VM, same setup as bronze + silver:

```
# server
cd C:\Users\Dragos\proelev\src\backend
python -m alembic upgrade head
python -m uvicorn main:app --host 0.0.0.0 --port 8000 \
    --ssl-keyfile certs/key.pem --ssl-certfile certs/cert.pem
```

Then point JMeter at your peer's `https://<their-ip>:8000` per the
instructions in `attack/README.md`. Watch their admin panel light
up with red `429`s and a new observation entry within seconds.

For Wireshark, ask them to also start an HTTP run on port 8080 as
a sacrificial target, capture once, and follow the TCP stream to
show the cleartext password. Then point Wireshark at the HTTPS port
and show the opaque TLS handshake.

## How to run

Local dev (single machine):
```
cd src/backend
python -m alembic upgrade head        # creates / migrates the .db file
python -m uvicorn main:app --reload --port 8000
```

Cross-machine demo (server on machine A, client on machine B):
```
# machine A (server) — find the LAN IP first, e.g. 192.168.1.42
python -m alembic upgrade head
python -m uvicorn main:app --host 0.0.0.0 --port 8000

# machine B (client) — make a .env.local in the project root
echo "VITE_API_URL=http://192.168.1.42:8000" > .env.local
npm run dev -- --host
```

Tests:
```
cd src/backend
python -m pytest -q                    # 117 tests
python -m pytest --cov=. --cov-report=term-missing
```

# ProElev — Database design

This document covers the persistence layer added in Assignment 3 (Bronze).

## Stack

- **Database:** SQLite (file `proelev.db` next to the backend, configurable via
  `DATABASE_URL`). Picked over Postgres/MySQL because the assignment forbids
  manual schema and SQLite needs zero install on the demo machine, while still
  being a real relational DB with ACID transactions, foreign keys, check
  constraints, and indexes.
- **ORM:** SQLAlchemy 2.0 — the most widely used Python ORM, mature, type-safe,
  works first-class with FastAPI through a `Depends(get_db)` session pattern.
- **Migrations:** Alembic — official migration tool for SQLAlchemy. The schema
  is **not** written by hand; it is autogenerated from the ORM model classes
  (`models.py`) with `alembic revision --autogenerate`, then applied with
  `alembic upgrade head`.

## 3NF proof, table by table

A relation is in **3NF** iff every non-key attribute is:
1. atomic (1NF), and
2. fully functionally dependent on the whole primary key (2NF), and
3. non-transitively dependent on the primary key (3NF — no `non-key → non-key`
   functional dependency).

All six tables use a single-column surrogate `id` primary key, so 2NF
(no partial dependency on a composite key) is trivially satisfied.

### subject `(id PK, name UNIQUE)`
1NF: scalar columns. 2NF: trivial. 3NF: `name` depends only on `id` — there is
no other non-key attribute, so no transitive dependency is possible. ✅

### school_class `(id PK, name UNIQUE)`
Same shape as `subject`. ✅

### homework `(id PK, title, subject_id FK, class_id FK, due_date, description, file_name)`
1NF: every column is scalar. There are no list-valued or nested fields.
2NF: trivial (single-column PK).
3NF: each non-key attribute depends only on `id`.
- `title`, `due_date`, `description`, `file_name` — properties of the homework
  itself, no functional dependency on each other.
- `subject_id` and `class_id` — FK columns; they reference the lookup tables.
  Crucially, the **subject name** and **class name** are *not* stored in this
  table — they live exactly once in `subject.name` and `school_class.name`.
  This is the change versus the in-memory model: previously the same string
  `"Matematică"` was repeated in every row, which was a transitive dependency
  (`subject_name` depended on `subject_id` if we had introduced one). After
  normalising into the lookup tables that transitive dependency is gone. ✅

### student `(id PK, homework_id FK, name, date_time, grade)`
1NF: scalar. 2NF: trivial. 3NF: each non-key attribute depends only on the
student's `id`. `name`, `date_time`, `grade` are independent of each other.
A `CHECK (grade IS NULL OR grade BETWEEN 1 AND 10)` constraint enforces the
domain at the DB level, not just in Pydantic. ✅

### comment `(id PK, homework_id FK, author, text, created_at)`
Identical analysis to `student`. ✅

### user `(id PK, email UNIQUE, password, name)`
Standalone table, no FKs. `email` is unique, all other attributes depend
only on `id`. ✅

### Why the current schema avoids the most common 3NF trap

Embedding subject/class as plain strings inside `homework` would technically
still be in 3NF if you treat the strings as atomic values with no other
attributes about them. The reason we extracted lookup tables is twofold:
(1) it eliminates string repetition (storage win on real datasets), and
(2) it makes adding attributes to subjects (like a colour or icon) trivial
without restructuring `homework` — i.e. it future-proofs the schema against
a 3NF violation that *would* appear the moment subjects acquire any second
attribute.

## Silver additions — roles, permissions and chat

### Auth/role schema (relational, in the same SQLite DB)

```
 ┌────────────┐         ┌──────────────────┐         ┌──────────────┐
 │ role       │1───────*│ role_permission  │*───────1│ permission   │
 │ id (PK)    │         │ role_id (PK,FK)  │         │ id (PK)      │
 │ name UNIQ  │         │ permission_id PK │         │ code UNIQ    │
 └────────────┘         └──────────────────┘         └──────────────┘
       │1
       │
       │*
 ┌────────────┐
 │ user       │   email UNIQ, role_id FK NOT NULL
 │ id (PK)    │
 │ email      │
 │ password   │
 │ name       │
 │ role_id FK │
 └────────────┘
```

`role` and `permission` are joined many-to-many through `role_permission`.
A user has exactly one `role`. Both tables are in 3NF — single-column PKs,
every non-key attribute (`role.name`, `permission.code`) depends only on `id`.
The seeder fills two roles (`admin`, `user`) and 15 permission codes; admin
gets all of them, normal users get a read-and-comment subset.

The migration that adds these tables (`alembic/versions/173a9d4e9ae9_*`) seeds
the role/permission rows **inside** the `upgrade()` function so a NOT NULL
`user.role_id` can be added safely (existing user rows get backfilled to admin
before the default is dropped).

### Chat — TinyDB (NoSQL) + WebSockets

The chat layer is the silver "real-time chat with NoSQL + WebSockets"
requirement. We deliberately use a **separate** datastore from the SQL one,
because chat messages are append-only document data and SQL is overkill for
them.

**Storage:** TinyDB, a single-file JSON document store. Path is
`./chat.json` by default, configurable via `CHAT_DB_PATH`.

**Two collections:**
- `rooms` — `{id, type, name, participants[]}` where type is `global`, `dm`,
  or `room`.
- `messages` — `{id, room_id, author_id, author_name, text, created_at}`.

**Room types:**
- `global` — auto-created, everyone joins it on connection. One per server.
- `dm` — created on demand when a user clicks another user's name. The
  `participants` array is sorted, so look-up is idempotent (`get_or_create_dm`).
- `room` — special topic rooms, **admin only** can create them. The chosen
  user IDs go into `participants`; non-participants get 403 on history reads
  and silent ignores on WebSocket subscribes.

**WebSocket protocol** at `/chat/ws`:
- `{type:"hello", user_id, user_name}` → server replies `{type:"ready"}` and
  auto-subscribes the client to the global room.
- `{type:"subscribe", room_id}` → server adds room to the client's set if the
  user is allowed to see it.
- `{type:"message", room_id, text}` → server persists via TinyDB and broadcasts
  `{type:"message", room_id, message:{...}}` to every client subscribed to
  that room.

**How to demo two-user chat:**
1. Start the server: `python -m uvicorn main:app --host 0.0.0.0 --port 8000`.
2. On the client machine, run the frontend with `VITE_API_URL` pointing at
   the server.
3. Open one browser window and log in as `admin@proelev.ro` / `Admin123`.
4. Open a second browser window (or a private/incognito tab so sessionStorage
   is independent) and log in as `user@proelev.ro` / `Parola123`.
5. Click the chat button (💬) in the top right of either window. Both windows
   are auto-subscribed to the **Global** room. Type a message in one — it
   appears in the other instantly.
6. To DM, click the other user's name in the **Persoane** list. The DM room
   is created on first message and reused after that.
7. To create a topic room, log in as admin, type a name in the
   "Camera nouă" input and click *Creează*. All other users get added
   automatically.

### Frontend role gating

After login, the user object (including `role` and the `permissions[]` array)
is saved to `sessionStorage`. `src/utils/auth.js` exposes `hasPerm(code)` and
`isAdmin()` so views can hide buttons:
- "ADAUGĂ TEMĂ" button on `/homeworks` is hidden unless `homework_create`.
- "Șterge" button on every homework row is hidden unless `homework_delete`.
- "MODIFICĂ" button on the homework detail page is hidden unless
  `homework_update`.
- "Camera nouă (admin)" panel inside the chat sidebar only renders when
  `isAdmin()` is true.

The backend also enforces the admin-only chat-room creation at the API
level (returns 403 to non-admin callers).

## Gold additions — audit logging + malicious-behaviour detection

### action_log + observation tables

```
 ┌──────────────────────────┐
 │ action_log               │
 │ id (PK)                  │
 │ user_id     FK→user      │   nullable, anonymous hits get null
 │ role_id     FK→role      │   captured at log time so role changes
 │ action       TEXT        │   short code, e.g. "homework.delete"
 │ target_type  TEXT        │   "homework" | "student" | "comment" | ...
 │ target_id    INT         │   id parsed out of the URL
 │ method       TEXT        │   GET / POST / PUT / DELETE
 │ path         TEXT        │   raw URL path
 │ status_code  INT         │   HTTP status returned
 │ ip_address   TEXT        │   request.client.host
 │ details      TEXT        │   JSON blob (e.g. query string)
 │ created_at   DATETIME    │   indexed
 └──────────────────────────┘
 indexes: (user_id, created_at) and (created_at) — drives detector queries

 ┌──────────────────────────┐
 │ observation              │
 │ id (PK)                  │
 │ user_id     FK→user UNIQ │   one row per flagged user
 │ reason      TEXT         │   semicolon-joined list of triggered rules
 │ score       INT          │   highest score seen so far
 │ first_flagged_at DATETIME│   never overwritten
 │ last_flagged_at  DATETIME│   updated on every fresh flag
 │ dismissed   INT (0|1)    │   admin can clear, fresh flag re-opens
 └──────────────────────────┘
```

Both tables are in 3NF — single-column PKs, every non-key attribute depends
only on the row id.

### Audit middleware (`audit_middleware.py`)

Registered globally on the FastAPI app. Runs after every HTTP request, in
this order:

1. Look at `path` — skip the OpenAPI/Swagger noise (`/docs`, `/openapi.json`,
   `/redoc`, `/favicon.ico`) and the health check (`/`).
2. Read `X-User-Id` header (sent automatically by `api.js` after login). If
   absent or unparseable, `user_id` is null — anonymous probes are still
   logged.
3. Classify the route through `_ROUTE_RULES` (a method+path regex table) into
   a short action code like `homework.delete` or `chat.dm.open`. Unknown
   routes get a generic `http.<method>` code so even unexpected traffic shows
   up in the log.
4. Insert the `ActionLog` row with method, path, status, IP, role, and the
   JSON-encoded query string in `details`.
5. If the request was authenticated, run `detector.update_observation(db,
   user_id)` synchronously — this is intentional, the lab teacher should see
   the observation list update on the very next admin-panel refresh, no
   background task to wait for.

Detector failures are caught and rolled back so they never break the user's
request.

### Detector rules (`detector.py`)

Tunable constants at the top of the file. Each rule scans a 60-second rolling
window of the user's `action_log` rows and contributes points to the user's
score. Score `>= 10` flags the user into `observation`.

| Rule                  | Trigger                                       | Points |
| --------------------- | --------------------------------------------- | ------ |
| Request flood         | `> 60` requests in the window                 | 5      |
| Mass delete           | `> 5` successful DELETEs in the window        | 7      |
| Forbidden spam        | `> 3` HTTP 403s in the window                 | 6      |
| Validation spam       | `> 10` HTTP 422s in the window (fuzzing)      | 4      |
| Privilege escalation  | non-admin attempting an admin-only action     | 10     |

Privilege escalation is the loudest rule on purpose — even a single attempt by
a normal user to hit `homework.delete`, `chat.room.create`,
`admin.observation.read`, etc. immediately puts them on the observation list.

When a user is re-flagged, `first_flagged_at` is preserved (audit trail) and
`last_flagged_at` is bumped to now. A previously dismissed observation is
automatically un-dismissed if the user gets flagged again.

### Admin endpoints (`routers/admin.py`)

All three endpoints take `user_id` as a query param and `_require_admin`
returns 403 if the caller is not an admin.

- `GET /admin/logs?user_id=…&page=1&pageSize=50&only_user_id=…` — paginated,
  newest first, optionally filtered to a single user. Each row includes the
  user name and role at log time.
- `GET /admin/observations?user_id=…&include_dismissed=false` — flagged users
  with name, email, role, score, reason, first/last seen, dismissed flag.
- `POST /admin/observations/{flagged_user_id}/dismiss?user_id=…` — clears the
  flag (sets `dismissed=1`).

### Admin Panel UI (`/admin`)

Vue view that auto-refreshes every 5 seconds, visible only to users with the
admin role (route guard plus the `ADMIN` sidebar item is conditional on
`isAdmin()`). Two cards stacked vertically:

1. **Lista de observație** — table of currently-flagged users with a
   `Dismiss` button per row. Toggle to include previously-dismissed entries.
2. **Activitate recentă** — color-coded action log table (HTTP method pills,
   status code badges). Filter by user id.

### How to demo on submission day

1. Start the server: `python -m alembic upgrade head` then
   `python -m uvicorn main:app --host 0.0.0.0 --port 8000`.
2. Log in as `admin@proelev.ro` in one browser, navigate to **ADMIN** in the
   sidebar — observation list is empty, action log shows your login.
3. In a second browser (incognito tab), log in as `user@proelev.ro`.
4. As the normal user, click `Șterge` in the homeworks list (it's hidden in
   the UI but you can hit it via the network — open DevTools, run
   `fetch('http://<server>:8000/homeworks/1', {method:'DELETE',
   headers:{'X-User-Id':'2'}})` from the console).
5. Within 5 seconds the admin panel shows the user with score `10+` and
   reason "privilege escalation: tried homework.delete as user".
6. Show the `Dismiss` button clearing the row, and the action log card filling
   up with every request.

## How to run

Local dev (single machine):
```
cd src/backend
python -m alembic upgrade head        # creates / migrates the .db file
python -m uvicorn main:app --reload --port 8000
```

Cross-machine demo (server on machine A, client on machine B):
```
# machine A (server) — find the LAN IP first, e.g. 192.168.1.42
python -m alembic upgrade head
python -m uvicorn main:app --host 0.0.0.0 --port 8000

# machine B (client) — make a .env.local in the project root
echo "VITE_API_URL=http://192.168.1.42:8000" > .env.local
npm run dev -- --host
```

Tests:
```
cd src/backend
python -m pytest -q                    # 117 tests
python -m pytest --cov=. --cov-report=term-missing
```
